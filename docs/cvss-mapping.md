# CAWASMA context-to-CVSS mapping

CAWASMA keeps the official CVSS v3.1 base score unchanged and computes a
separate environmental score. Only CVSS Security Requirements (`CR`, `IR`,
`AR`) are overridden; modified base metrics (`MAV`, `MAC`, `MPR`, `MUI`, `MS`,
`MC`, `MI`, `MA`) remain Not Defined/equal to the base metrics. This preserves
the distinction between a rule's technical exploitability and the importance
of the affected deployment asset.

The implementation is [config/cvss_mapping.yaml](../config/cvss_mapping.yaml).
The values `L`, `M`, and `H` are CVSS Low, Medium, and High requirements;
`X` is Not Defined. Under the CVSS v3.1 environmental formula, requirements
weight the impact metrics at 0.5, 1.0, and 1.5 respectively; `X` contributes
1.0 and therefore preserves the base metric.

## Sensitivity classes

| Class | Definition | CR | IR | AR | CVSS v3.1 rationale |
|---|---|:---:|:---:|:---:|---|
| LOW | Public, non-sensitive pages and static content. | X | X | X | Not Defined preserves the base impact because context has not established a higher asset requirement. |
| MEDIUM | Ordinary user data, profiles, and user-facing operations. | M | M | M | Medium requirements represent normal business value without asserting privileged or mission-critical impact. |
| HIGH | Authentication, token, session, and account-control surfaces. | H | M | M | Authentication data has high confidentiality importance; account operations have medium integrity and availability importance. |
| CRITICAL | Administrative, privileged, payment, and high-impact financial operations. | H | H | H | Loss of confidentiality, integrity, or availability can materially affect privileged control or financial operations. |

These are sensitivity classes, not claims that a vulnerability is exploitable.
The classifier supplies context; the check's base vector still describes the
vulnerability's attack conditions and inherent impact.

## Body signals

| Signal | Meaning | CR | IR | AR | CVSS v3.1 rationale |
|---|---|:---:|:---:|:---:|---|
| CREDENTIALS | Passwords, session tokens, API keys, or private keys. | H | H | M | Credential disclosure strongly affects confidentiality and can enable unauthorized integrity impact; account unavailability is secondary. |
| PII | Personal data such as email addresses, phone numbers, or national IDs. | H | M | X | PII exposure is primarily a confidentiality loss; alteration matters for data integrity, while availability is not established. |
| FINANCIAL | Payment records, card data, IBANs, or financial transactions. | H | H | M | Financial data requires strong confidentiality and transaction integrity; service availability has meaningful but secondary importance. |
| INTERNAL_IP | RFC 1918, loopback, or link-local addresses. | M | X | X | Internal topology is reconnaissance-sensitive and raises confidentiality modestly, but does not by itself establish integrity or availability impact. |

The shared contract currently exposes exactly these four `BodySignal` values.
Secret keys are classified under `CREDENTIALS`; a stack trace is evidence for
information disclosure but is not currently a body signal. Adding separate
`SECRET_KEY` or `STACK_TRACE` enum members requires a coordinated contract and
classifier change before adding mapping rows.

## Combination rule

For each requirement independently, CAWASMA takes the maximum of the endpoint
class row and every detected body-signal row. Thus a signal can only preserve
or raise a requirement; it cannot lower one supplied by the endpoint class.
The mapping does not modify exploitability metrics or invent a new attack
vector.

## Worked examples

The examples below use the `cvss` Python package (`CVSS3`) and append only
`CR`, `IR`, and `AR` to each base vector. `base` is the official base score;
`public` uses `LOW` (`X/X/X`), and `admin` uses `CRITICAL` (`H/H/H`).
The exact output is generated by
[eval/harness/mapping_demo.py](../eval/harness/mapping_demo.py).

| Example | Base vector | Base | Public | Admin |
|---|---|---:|---:|---:|
| Missing HSTS | `CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N` | 5.9 | 5.9 | 7.7 |
| Missing CSP | `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N` | 5.4 | 5.4 | 6.4 |
| Version disclosure | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N` | 5.3 | 5.3 | 6.1 |
| Missing session cookie HttpOnly | `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:N` | 8.1 | 8.1 | 8.8 |
| Unauthenticated sensitive endpoint | `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N` | 9.1 | 9.1 | 9.8 |

The public/admin contrast is a prioritization effect: the same technical
finding receives a higher environmental score when the affected asset has
higher security requirements. It does not change the official base score.

## Can a mapped score go down?

With this mapping, no. `LOW` uses `X/X/X`, which is the CVSS neutral
environmental value, and all other class/signal values are `M` or higher.
Because combination is `max`, no body signal can reduce a class requirement.
The examples satisfy `environmental_score >= base_score` (up to CVSS rounding).

If a future mapping assigns `L` to a class or signal, CVSS can legitimately
produce an environmental score below the base score: Low Security Requirements
mean that compromise of that impact dimension matters less for the assessed
environment. That is standards-valid, but it would conflict with CAWASMA's
current product rule that context is a prioritization uplift. The fix is to
use `X` for neutral/public context and reserve `L` for an explicitly documented
low-value asset policy; never clamp or rewrite the CVSS formula.
